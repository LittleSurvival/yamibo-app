# Yamibo App Updater Release Guide

This document describes the manifest used by the in-app updater and the Android APK release flow.

## Manifest

The app checks for updates from the GitHub repository `lmc2007/yamibo-app`. Because GitHub direct access can be slow, the client prefers third-party GitHub acceleration mirrors for the update feed and falls back to GitHub direct only when the mirrors are unavailable:

1. `https://github.cnxiaobai.com/https://raw.githubusercontent.com/lmc2007/yamibo-app/update-release/update/stable.json`
2. `https://gh.halonice.com/https://raw.githubusercontent.com/lmc2007/yamibo-app/update-release/update/stable.json`
3. `https://ghproxy.sakuramoe.dev/https://raw.githubusercontent.com/lmc2007/yamibo-app/update-release/update/stable.json`
4. `https://gh.padao.fun/https://raw.githubusercontent.com/lmc2007/yamibo-app/update-release/update/stable.json`
5. `https://gh.jasonzeng.dev/https://raw.githubusercontent.com/lmc2007/yamibo-app/update-release/update/stable.json`
6. `https://ghproxy.mirror.skybyte.me/https://raw.githubusercontent.com/lmc2007/yamibo-app/update-release/update/stable.json`
7. `https://raw.githubusercontent.com/lmc2007/yamibo-app/update-release/update/stable.json` (GitHub direct)

Per-source update-check timeouts are enforced in `DefaultAppUpdateRepository`: proxy feeds use 5 seconds and the GitHub direct feed uses 10 seconds.

All seven endpoints serve the same GitHub `update-release` feed. `gh-proxy.com` is not used for update checks — it only accelerates APK downloads. Add or remove check mirrors only after verifying them with `tools/check-update-mirrors.ps1`.
`update/manifest.json` is the manually edited source of truth in the source repo. `update/stable.json` is generated by `syncStableManifest`.

The client walks the sources in order and automatically falls back to the next endpoint when a source fails to fetch or decode (network error, non-2xx HTTP, JSON error, or an HTML error page); only when every source fails does the check report failure, with per-source error details. A ready manifest whose `versionCode` is not newer than the installed app is treated as a stale/cached mirror and the client keeps scanning the remaining sources instead of reporting "up to date" from the stale one. The client remembers the mirror that last returned a usable manifest (or the mirror that produced the final update/preparing result) and rotates it to the front, so the next check tries the last successfully detected mirror first.


Android APK downloads: GitHub Release assets are downloaded through `https://gh-proxy.com/<original-url>` first, and fall back to the GitHub direct URL when the proxy attempt fails.

For Gitea APK assets, publish through the API and write the upload response's `browser_download_url` into the
published manifest. Do not construct `/releases/download/...` URLs: gitea.com may redirect those web routes to login.
The workflow must anonymously probe the returned URL and confirm the APK ZIP signature before publishing the manifest.
Source manifests must always keep `isReady=false`; published manifests are generated by the release workflow after the APK has been uploaded.

```json
{
  "channel": "stable",
  "versionName": "1.2.0",
  "versionCode": 120,
  "isReady": false,
  "minVersionCode": 100,
  "releaseNotes": "Fixes and improvements.",
  "assets": []
}
```

Fields:

- `isReady`: source manifests must be `false`. The release workflow publishes `true` only after APK upload succeeds.
- `versionCode`: the numeric value compared with the installed Android `versionCode`. Increase this for every release.
- `versionName`: display version shown to users.
- `minVersionCode`: optional lower bound for future forced-update policy. The app records it now but does not force updates yet.
- `releaseNotes`: plain text shown in the update screen.
- `releaseUrl`: published-only field opened when the user taps the release-page action.
- `assets`: published-only installable files. Android currently accepts `type = "universal-apk"` or `"apk"`.
- `sha256`: required for production releases. The app verifies it before opening the installer.
- `size`: optional byte count used by the progress UI.

## Android APK Release Flow

1. Update `versionCode` and `versionName` in `composeApp/build.gradle.kts`.
2. Update `update/manifest.json`.
3. Run manifest sync and validation:

```powershell
.\gradlew syncStableManifest validateUpdateManifest --console=plain
```

The build fails if `composeApp/build.gradle.kts`, `update/manifest.json`, `update/stable.json`, and `update/changelogs/{versionCode}.changelog` are inconsistent.
It also fails if source manifests set `isReady=true`, contain `releaseUrl`, or contain non-empty `assets`.

Manual APK flow:

1. Build a release APK:

```powershell
.\gradlew :composeApp:assembleRelease --console=plain
```

3. Sign the APK if the build is not already configured with a release signing config.
4. Calculate SHA-256:

```powershell
Get-FileHash .\composeApp\build\outputs\apk\release\composeApp-release.apk -Algorithm SHA256
```

5. Upload the APK to GitHub Releases.
6. Upload/copy the same APK to Gitee and Gitea release assets.
7. Generate target-specific published update folders with `isReady=true`, `releaseUrl`, and APK `assets`.
8. Validate each target folder with `validatePublishedUpdateManifest`.
9. Push the GitHub-targeted update folder to the GitHub `update-release` branch, and push the Gitee/Gitea-targeted folders to their mirror repos.
10. Open the app Settings -> App updates -> Check update.

Do not publish Gitee or Gitea ready manifests whose APK asset URL points back to GitHub.

## iOS Update Flow

iOS cannot install an IPA directly from inside a normal App Store/TestFlight app. The app updater therefore only checks the manifest and opens `releaseUrl`.

Recommended options:

- App Store: use an App Store product URL as `releaseUrl`.
- TestFlight: use the TestFlight invite/app URL.
- Enterprise/MDM/internal distribution: use the organization's HTTPS landing page. The actual install must be handled by Safari, MDM, or Apple's enterprise install flow.

## Mirror Maintenance

The update feed lives in the GitHub repository `lmc2007/yamibo-app` (`update-release` branch). The client reaches it through third-party GitHub acceleration mirrors; the active check list is `DefaultAppUpdateRepository.sources`:

- `github.cnxiaobai.com`
- `gh.halonice.com`
- `ghproxy.sakuramoe.dev`
- `gh.padao.fun`
- `gh.jasonzeng.dev`
- `ghproxy.mirror.skybyte.me`

`gh-proxy.com` is only used to accelerate APK downloads and is not part of the update check sources.

If a mirror dies or changes its URL format, update `DefaultAppUpdateRepository.sources`, `tools/check-update-mirrors.ps1`, and this document together.
For the release workflow's Gitee/Gitea release-mirror repositories and secrets, see `dev-docs/gitea-update-mirror-setup.md`.

The script uses the same timeout policy as the app: 5 seconds per proxy feed and 10 seconds for GitHub direct.

Verify all check mirrors and the download proxy before a release:

```powershell
powershell -NoProfile -File .\tools\check-update-mirrors.ps1
```

The script requests the GitHub feed directly and through every check mirror, warns when a mirror serves a stale `versionCode`, and HEAD-checks the GitHub APK asset both directly and through `https://gh-proxy.com/`.
