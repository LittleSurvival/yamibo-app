# Yamibo App Updater Release Guide

This document describes the manifest used by the in-app updater and the Android APK release flow.

## Manifest

The app checks these manifests in order:

1. `https://raw.githubusercontent.com/LittleSurvival/yamibo-app/update-release/update/stable.json`
2. `https://gitee.com/LittleSurvival/ymb-apk-release/raw/main/update/stable.json`
3. `https://gitea.com/api/v1/repos/LittleSurvival/ymb-apk-release/raw/update/stable.json?ref=main`

Keep the same release metadata in each published `update/stable.json`, but asset URLs must be target-specific. The GitHub feed points to GitHub Release APK assets, the Gitee feed points to Gitee Release APK assets, and the Gitea feed points to Gitea Release APK assets. The Gitee/Gitea URLs are intended for users who cannot reliably reach GitHub.
`update/manifest.json` is the manually edited source of truth in the source repo. `update/stable.json` is generated by `syncStableManifest`.

For Gitea APK assets, publish through the API and write the upload response's `browser_download_url` into the
published manifest. Do not construct `/releases/download/...` URLs: gitea.com may redirect those web routes to login.
The workflow must anonymously probe the returned URL and confirm the APK ZIP signature before publishing the manifest.
Source manifests must always keep `isReady=false`; published manifests are generated by the release workflow after the APK has been uploaded.

```json
{
  "channel": "stable",
  "versionName": "1.2.0",
  "versionCode": 120,
  "isReady": false,
  "minVersionCode": 100,
  "releaseNotes": "Fixes and improvements.",
  "assets": []
}
```

Fields:

- `isReady`: source manifests must be `false`. The release workflow publishes `true` only after APK upload succeeds.
- `versionCode`: the numeric value compared with the installed Android `versionCode`. Increase this for every release.
- `versionName`: display version shown to users.
- `minVersionCode`: optional lower bound for future forced-update policy. The app records it now but does not force updates yet.
- `releaseNotes`: plain text shown in the update screen.
- `releaseUrl`: published-only field opened when the user taps the release-page action.
- `assets`: published-only installable files. Android currently accepts `type = "universal-apk"` or `"apk"`.
- `sha256`: required for production releases. The app verifies it before opening the installer.
- `size`: optional byte count used by the progress UI.

## Android APK Release Flow

1. Update `versionCode` and `versionName` in `composeApp/build.gradle.kts`.
2. Update `update/manifest.json`.
3. Run manifest sync and validation:

```powershell
.\gradlew syncStableManifest validateUpdateManifest --console=plain
```

The build fails if `composeApp/build.gradle.kts`, `update/manifest.json`, `update/stable.json`, and `update/changelogs/{versionCode}.changelog` are inconsistent.
It also fails if source manifests set `isReady=true`, contain `releaseUrl`, or contain non-empty `assets`.

Manual APK flow:

1. Build a release APK:

```powershell
.\gradlew :composeApp:assembleRelease --console=plain
```

3. Sign the APK if the build is not already configured with a release signing config.
4. Calculate SHA-256:

```powershell
Get-FileHash .\composeApp\build\outputs\apk\release\composeApp-release.apk -Algorithm SHA256
```

5. Upload the APK to GitHub Releases.
6. Upload/copy the same APK to Gitee and Gitea release assets.
7. Generate target-specific published update folders with `isReady=true`, `releaseUrl`, and APK `assets`.
8. Validate each target folder with `validatePublishedUpdateManifest`.
9. Push the GitHub-targeted update folder to the GitHub `update-release` branch, and push the Gitee/Gitea-targeted folders to their mirror repos.
10. Open the app Settings -> App updates -> Check update.

Do not publish Gitee or Gitea ready manifests whose APK asset URL points back to GitHub.

## iOS Update Flow

iOS cannot install an IPA directly from inside a normal App Store/TestFlight app. The app updater therefore only checks the manifest and opens `releaseUrl`.

The release workflow builds an unsigned iPhone device IPA with the Xcode
`Release` configuration and publishes the same `yamibo-<channel>-v<version>-unsigned.ipa`
to the GitHub, Gitee, and Gitea releases alongside the Android APK. Its bundle
version and build number come from `update/manifest.json`.

The manual `release.yml` workflow follows this dependency graph:

```text
check ─┬─ build_android ─┬─ release
       └─ build_ios ─────┘
```

`check` validates the changelog, manifest/app version consistency, source manifest
rules, existing tag target, and presence of the Android signing and mirror
credentials. Both builds start only after it succeeds and use the same workflow
commit. The Android job signs and verifies the APK; the iOS job packages the
unsigned device Release build. `release` waits for both artifacts, verifies the
APK checksum and IPA presence, rechecks/creates the source tag, then publishes
both files to all three hosts. The tag is created only after successful builds;
an existing tag for the same commit permits reruns, while a conflicting tag fails
in `check`. Before preparing mirror tags, the release job regenerates
`update/stable.json` in its own checkout. Published feeds are generated, validated,
and synced after the asset uploads.

A failed check prevents both builds; a failed or cancelled build prevents
publication. If a later
upload fails, inspect all three releases and rerun the failed release job to
complete the publication before declaring the release complete. Mirror reruns
recreate their releases and upload both assets together.

The IPA is unsigned and cannot be installed as-is. Users must sign and install it
using a compatible tool and their own Apple account or signing credentials. Free
Apple personal-team provisioning expires after seven days and requires renewal.
Compatibility depends on the signing tool, the user's provisioning profile,
bundle identifier and capabilities. This distribution path is separate from
App Store or TestFlight publication. The update manifests continue to describe
the Android APK; iOS users open the release page to obtain the IPA.

Recommended options:

- App Store: use an App Store product URL as `releaseUrl`.
- TestFlight: use the TestFlight invite/app URL.
- Enterprise/MDM/internal distribution: use the organization's HTTPS landing page. The actual install must be handled by Safari, MDM, or Apple's enterprise install flow.

## Mirror Maintenance

Recommended mirror URLs:

- GitHub: `https://github.com/LittleSurvival/yamibo-app`
- Gitee: `https://gitee.com/LittleSurvival/ymb-apk-release`
- Gitea: `https://gitea.com/LittleSurvival/ymb-apk-release`

If the mirror owner/name changes, update `DefaultAppUpdateRepository.sources` and this document together.
For GitHub Actions secret setup and Gitea repository initialization, see `dev-docs/gitea-update-mirror-setup.md`.
